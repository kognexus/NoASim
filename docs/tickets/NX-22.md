# NX-22: Policy computer or classic controller

See [PLAN.md](../PLAN.md) for the behaviours (B*) and hypotheses (H*) referenced here.
Added after the owner's first review: the arm must work with either a VLA on a
Thor-class computer or a classic robot controller, and switch between them.

## Acceptance criteria

- [x] A classic-controller host profile: the robot program's path sampled on a fixed
  1–4 kHz loop, never late, IK every tick, a setpoint to every joint each tick
- [x] The same joints follow it, unchanged
- [x] Switching between the policy computer and the classic controller task by task,
  without a jump
- [x] A classic controller can take over mid-motion, smoothly
- [x] Demo selector

## Tests

- `sim/src/harness/hosts.test.ts`:
  - a classic controller at 1 kHz and at 4 kHz drives a pick and place within 2 mm RMS,
    with no faults and six setpoints every controller tick;
  - classic, policy, classic, policy tasks in a row each stay as accurate as on their
    own (path error maximum under 5 mm classic, 15 mm policy);
  - a classic controller taking over a running policy task moves the tool less roughly
    than the policy computer did, with no faults
- The H2 tests (`interpolation.test.ts`, `motion.test.ts`) still pass: the policy modes
  are unchanged

## Log

- 2026-10-21: **Host side.** `InterpolationMode` gains `"classic"` (`sim/src/host/host.ts`):
  - `ClassicController` (`sim/src/host/motion.ts`) runs a task as a program, with no
    policy. On a fixed loop (`loopHz`, 1 kHz by default, up to the 4 kHz bus rate) it
    samples the programmed tool path, solves IK warm-started from the last solution and
    streams position and velocity to every joint.
  - Like any robot controller it first moves to where the program starts: a quintic joint
    move at no more than 0.5 rad/s, at least 0.3 s, and none when the arm is already
    there. The program then runs that much later.
- **Joint side: nothing new.** Starting a task sends `Settings.interpolation`: the joints
  follow setpoints for the classic controller (and for the H2 "central" baseline) and
  interpolate goals for the policy computer. The setpoint follower, which holds each
  setpoint with its velocity, was enough for a 1 kHz stream (measured below); no
  interpolation between setpoints was needed.
- **Measured** (KX-6, seed 7; path error RMS (max), tool jerk RMS):

| Task | VLA computer, joints interpolate | VLA computer, host interpolates at 250 Hz | Classic, 1 kHz | Classic, 4 kHz |
|---|---|---|---|---|
| Figure of eight | 1.9 (11.6) mm, 254 m/s³ | 7.8 (33.9) mm, 508 m/s³ | 0.9 (1.8) mm, 22 m/s³ | 0.9 (1.7) mm, 30 m/s³ |
| Pick and place | 1.6 (5.7) mm, 191 m/s³ | 7.8 (36.3) mm, 565 m/s³ | 1.1 (4.5) mm, 28 m/s³ | 1.1 (4.4) mm, 42 m/s³ |
| Fast reach | 24.4 (109) mm, 734 m/s³ | 46.4 (198) mm, 668 m/s³ | 6.0 (21.9) mm, 58 m/s³ | 5.9 (21.4) mm, 58 m/s³ |

  The classic controller is far more accurate, but it isn't a fair race: it samples the
  exact path with no latency, while the policy computer knows only 15 Hz goals that
  arrive 30 ms late with jitter and losses. The comparison that matters for a VLA host
  is the left two columns (H2). 4 kHz buys nothing over 1 kHz here: the 4 Hz joint
  servo, not the setpoint rate, limits tracking. A 4 kHz controller solves 34 000 IKs
  for a figure of eight.
- **Takeover mid-motion:** a policy figure of eight running for 2 s, then a classic
  controller started on the same program. Its lead-in was 0.3 s. The tool's largest
  speed change over 10 ms was 6.5 m/s², against 15.6 m/s² while the policy computer
  drove it, with no faults. The joints hold their last reference when the mode changes,
  then follow the new setpoints.
- **Demo:** a "Driven by" selector next to the task buttons (VLA computer at 15 Hz, or
  classic controller at 1 kHz). A running task restarts on the chosen computer. It lands
  with NX-24, which changes the same files.
